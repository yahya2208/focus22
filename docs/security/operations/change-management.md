# Change Management — عمليات كتابة Production (إلزامية)

**المرجع:** FOCUS v2.0 Strategic Reset (2026-08-03) · **المحفّز:** حادثة `04-2.1.6`
(تشغيل بروب يفترض أنه قراءة-only كتب في Production).
**النطاق:** كل عملية كتابة على قاعدة Production — `UPDATE` / `DELETE` / `INSERT` /
`CREATE` / `ALTER` / `DROP` / `GRANT` / `REVOKE` / استدعاء دالة ذات أثر كتابة.

> قاعدة الحكم: **"Production Is Sacred"**. أي عملية كتابة لا تحقق بنود هذا
> المستند تعتبر **مرفوضة** بغض النظر عن صحتها.

---

## 1) المبادئ الحاكمة (غير قابلة للتفاوض)

| المبدأ | المعنى العملي |
|---|---|
| **Production أولاً** | لا تُقدَّم السرعة على الأمان أو سلامة البيانات |
| **Evidence Before Apply** | لا تغيير دون أدلة مسبقة وخطة رجوع واضحة |
| **No Blind Writes** | لا UPDATE/DELETE/INSERT جماعي دون: عدد الصفوف المتوقع، الصفوف المتأثرة، السبب، طريقة التحقق |
| **No Assumptions** | كل ادعاء يدعمه استعلام/نتيجة تشغيلية، لا ظن |
| **Production Is Sacred** | التجارب في Development/Staging أولاً؛ Production ليست بيئة تجارب |

## 2) دورة الحياة الإلزامية لأي عملية كتابة

### 2.1 قبل التنفيذ (Pre-Apply) — كلها إلزامية

- [ ] **معرّف تغيير** — `CR-###` مسجل في `docs/security/operations/` (أو وفق
      اصطلاح الفرع) + وصف مختصر في الـ commit.
- [ ] **السبب** — أي شذوذ/حادث/متطلب يبرر الكتابة، مرجعاً بالأدلة.
- [ ] **SQL Preview** — السكربت الكامل مُعاين ومُراجَع قبلياً (نص حرفي).
- [ ] **الصفوف المتوقعة** — `expected row count` محسوب باستعلام
      `SELECT count(*)` بنفس شرط UPDATE/DELETE، ومُوثَّق.
- [ ] **الصفوف المتأثرة** — قائمة (أو شرط دقيق) تسمح بالتطابق الواحد-لواحد.
- [ ] **Snapshot/استرجاع** — إذا كانت البيانات ذات قيمة: نسخة/وسيلة استرجاع
      (الجدول المعني، أو الصفوف، أو PITR إن توفر).
- [ ] **خطة Rollback** — كيفية الرجوع إن كانت العملية قابلة للرجوع؛ وإن لم
      تكن قابلة، يُكتب ذلك صراحةً.
- [ ] **الموافقة** — موافقة صريحة (قراءة وسجل) قبل التنفيذ.
- [ ] **Checklist مكتملة** في ملف الـ CR نفسه قبل أي تنفيذ.

### 2.2 بعد التنفيذ (Post-Apply) — كلها إلزامية

- [ ] **عدد الصفوف الفعلي** — `GET DIAGNOSTICS` / `row_count` موثق.
- [ ] **مقارنة قبل/بعد** — ناتج استعلام التحقق قبل وبعد.
- [ ] **تحقق سلامة** — الشرط الأصلي عاد إلى القيمة الصحيحة، ولا صفوف زائدة.
- [ ] **التحقق من عدم وجود آثار جانبية** — أي تغيير غير متوقع يُعلَّق ويُحقق
      ولا يُغلق حتى يُفسَّر.

## 3) القواعد التشغيلية الدائمة (Phase D)

1. **لا SQL يكتب على Production مباشرة دون مراجعة** — دائماً عبر CR.
2. **سكربتات الفحص تكون Read-Only كلما أمكن** — وإذا تطلب اختبار ما كتابةً،
   يكون داخل `BEGIN; ... ROLLBACK;` وبدون أي `set_config(..., false)`
   (درس الحادث) ودون الاعتماد على `ROLLBACK` وحده كضمان.
3. **سكربتات الإصلاح تُوثَّق قبل التنفيذ** بالكامل (القسم 2.1).
4. **كل تغيير يحمل Change ID قابل للتتبع** في السجلات (git + هذا الدليل).
5. **أي بروب تحقق مستقبلي** يلتزم بقواعد `08-2.1.6-baseline-reverify-readonly.sql`
   (SELECT/EXPLAIN/كتالوج فقط — بنيوياً لا يمكنه الكتابة).

## 4) معايير الجودة (محرمات)

- ❌ لا حلول مؤقتة (يجب أن تُكتب الحلول بشكل نهائي قابل للصيانة).
- ❌ لا تجاوز للاختبارات.
- ❌ لا تعطيل لآليات الأمان (RLS/الحارس/EXECUTE) بهدف "تسريع الإصلاح".
- ❌ لا إزالة حماية لتسريع الإصلاح.
- ❌ لا دمج لأي كود غير مثبت بالأدلة.

## 5) Definition of Done (لأي مهمة/تغيير)

الكود مكتمل · الاختبارات ناجحة · التحقق التشغيلي ناجح · الأدلة محفوظة ·
التوثيق محدّث · لا آثار جانبية غير مفسرة.

## 6) Release Readiness (Phase E — قبل اعتماد Production)

كل البنود التالية خضراء: Build · TypeScript · ESLint · Tests · Runtime
Validation · Security Audit · RLS Audit · RPC Audit · Performance · Monitoring ·
Logging · Error Handling · Deployment · Rollback Plan · Documentation.
**لا يُنشر إذا بقي أي بند أحمر.**
