# ADR-001 — مبادئ التفويض المعمارية (Authorization Principles)

**الحالة:** مقترح للاعتماد — يُثبَّت كـ "لا يتغير أثناء التنفيذ" عند اعتماد بداية Phase 2.
**التاريخ:** 2026-08-02 · **المصدر:** `docs/security/phase2/00-permissions-inventory.md` + `01-duplication-analysis.md` + `02-authorization-layer-design.md` · **المرجع:** Baseline v4.0

---

## السياق (Context)
Phase 1 أثبتت أن الحماية الفعلية في قاعدة البيانات (RLS + EXECUTE + حارس الأدوار)، وأن التطبيق يحتوي أنظمة أدوار موازية وقواعد صلاحية مكررة (تصل إلى 6 مواضع لنفس القرار). بدون تثبيت المبادئ الآن، سيتغير التصميم أثناء التنفيذ ويتحول إلى هدف متحرك (نفس الدرس من `remediation-roadmap.md`).

## القرارات (Decisions) — ثابتة حتى إشعار مقرَّر

| # | القرار | الأثر |
|---|---|---|
| A1 | **Source of Truth = `users.role`** (قيمة صف في قاعدة البيانات، تُملأ من `handle_new_user` لا من `user_metadata`) | أي خريطة أدوار (App→Research) مشتقة منه؛ لا مصدر ثانٍ |
| A2 | **التفويض يُفرض في قاعدة البيانات أولاً** — RLS + EXECUTE + حارس داخل الدالة | الواجهة لا تملك وحدها أي قرار أمني |
| A3 | **Guards الواجهة للـ UX فقط** — إظهار/إخفاء وتوجيه، لا حماية | لا يُحذف RLS أبداً "لأن الواجهة تمنع" |
| A4 | **كل RPC من نوع SECURITY DEFINER تتحقق من صلاحية المتصل داخلياً** — إلا الاستثناءات الموثّقة في v4.0 (`handle_new_user`, `has_super_admin`, `increment_qr_counter`, `lookup_*`) | الدفاع لا يعتمد على GRANT وحده |
| A5 | **`app_role()` هي الأداة الوحيدة لقراءة دور المتصل** في SQL | تحل محل أي `EXISTS ... role` / قراءات مباشرة |
| A6 | **`is_admin()` هي المسند الوحيد لـ "أدمن"** (`role IN ('admin','super_admin')`) | يُستبدل بها كل نمط EXISTS المكرر (qr_codes + M9 × 3 + "Admins update user roles") |
| A7 | **لا منطق أدوار مكرر في React** — مصفوفة واحدة (`ROLE_PERMISSIONS` + `ROLE_CAPABILITY_MAP`)، `ProtectedRoute` بنظام حراسة واحد | إزالة `roleHierarchy` الهرمي الموازي و`HomeMenu.isAdmin` الأد-هوك |
| A8 | **RLS هي طبقة الإنفاذ النهائية** لكل الوصول للبيانات | أي وصول (App/خدمة/أداة) يمر بها؛ `is_research_role`/`has_super_admin` تُستدعى داخل السياسات |

## العواقب (Consequences)
- **إيجابي:** مصدر واحد لكل قرار → انجراف أقل، مراجعة أسرع، واختبارات أسهل (نفس مكاسب Phase 1).
- **سلبي/تكلفة:** إعادة كتابة سياسات الأدمن الحالية + توحيد الواجهة + إضافة حارس لكل RPC إدارية — كلها داخل خطة 2.1.
- **قيود:** أي دالة SECURITY DEFINER جديدة تُقيَّم ضد A4/A5 قبل اعتمادها.

## اعتماد هذا القرار (Acceptance)
يُثبَّت هذا المستند كمرجع عند اعتماد بداية Phase 2 ولا يُعدَّل أثناء التنفيذ؛ أي تعديل مستقبلي يمر بسجل تغييرات ADR.
