## A. Final Schema

### Table: `phone_view_counts`

Denormalized counter — the single source of truth for total + unique views.

```sql
CREATE TABLE public.phone_view_counts (
  device_id       text        PRIMARY KEY REFERENCES public.inventory(id) ON DELETE CASCADE,
  total_views     integer     NOT NULL DEFAULT 0,
  unique_views    integer     NOT NULL DEFAULT 0,
  last_viewed_at  timestamptz,
  updated_at      timestamptz NOT NULL DEFAULT now()
);

COMMENT ON TABLE  public.phone_view_counts IS 'Denormalized view counters per phone listing. Updated atomically by record_phone_view().';
COMMENT ON COLUMN public.phone_view_counts.device_id    IS 'FK → inventory(id). One row per phone.';
COMMENT ON COLUMN public.phone_view_counts.total_views   IS 'Count of accepted view events (post-dedup + rate-limit check).';
COMMENT ON COLUMN public.phone_view_counts.unique_views  IS 'Distinct dedup keys accepted for this device.';
COMMENT ON COLUMN public.phone_view_counts.last_viewed_at IS 'Timestamp of the most recent accepted view event.';
COMMENT ON COLUMN public.phone_view_counts.updated_at    IS 'Row-level update timestamp for optimistic concurrency.';
```

**Why these columns:**

| Column | Purpose |
|---|---|
| `device_id` PK | 1:1 with inventory — no junction needed, simple lookup. |
| `total_views` | Every accepted view event increments this. Used for "Views" display. |
| `unique_views` | Distinct `(dedup_key, device_id)` pairs within the active window. Used for "Unique Views" display. |
| `last_viewed_at` | Enables "most recently viewed" sort in admin without scanning events. |
| `updated_at` | Detect stale reads in admin UI; standard pattern in this codebase. |

### Table: `phone_view_events`

Append-only event log — the audit trail.

```sql
CREATE TABLE public.phone_view_events (
  id              bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  device_id       text        NOT NULL REFERENCES public.inventory(id) ON DELETE CASCADE,
  visitor_hash    text        NOT NULL,
  event_type      text        NOT NULL DEFAULT 'view'
                        CHECK (event_type IN ('card_view', 'detail_view')),
  is_unique       boolean     NOT NULL DEFAULT false,
  recorded_at     timestamptz NOT NULL DEFAULT now()
);

COMMENT ON TABLE  public.phone_view_events IS 'Append-only log of accepted view events. Used for unique-view dedup and analytics.';
COMMENT ON COLUMN public.phone_view_events.id           IS 'Monotonic event ID. Never reused.';
COMMENT ON COLUMN public.phone_view_events.device_id    IS 'FK → inventory(id). Which phone was viewed.';
COMMENT ON COLUMN public.phone_view_events.visitor_hash IS 'Client-supplied anonymous ID (^[a-f0-9]{16,64}$). Non-PII.';
COMMENT ON COLUMN public.phone_view_events.event_type   IS 'card_view = listing grid; detail_view = details page.';
COMMENT ON COLUMN public.phone_view_events.is_unique    IS 'true if this was the first event from this visitor_hash for this device within the dedup window.';
COMMENT ON COLUMN public.phone_view_events.recorded_at  IS 'Server-side timestamp (not client-submitted).';
```

**Indexes:**

```sql
-- Dedup check: "has this visitor seen this device in the last hour?"
CREATE INDEX idx_view_events_dedup
  ON public.phone_view_events (device_id, visitor_hash, recorded_at);

-- Analytics: "events for this device, ordered by time"
CREATE INDEX idx_view_events_device_time
  ON public.phone_view_events (device_id, recorded_at DESC);

-- Cleanup: "delete events older than 90 days"
CREATE INDEX idx_view_events_recorded_at
  ON public.phone_view_events (recorded_at);
```

**Retention:** Events older than 90 days are deleted by a scheduled job or on-demand. The counter table (`phone_view_counts`) is never affected by event cleanup — it is the permanent record.

## B. Identity Strategy

### Format

```
128-bit cryptographically random hex string
32 hex characters: [a-f0-9]{32}
Example: 4a7f3c1b9e2d8a0f5c6b1e4d7a9f3c2b
```

Generated by `crypto.getRandomValues(new Uint8Array(16))` — already implemented in `intent-tracking.ts:57-64`.

### localStorage key

```
focus_vid_v1
```

Already implemented. Server validates against `^[a-f0-9]{16,64}$`.

### Lifecycle

| Scenario | Behavior |
|---|---|
| **First visit** | `getVisitorHash()` generates a fresh 32-char hex ID, persists to `focus_vid_v1`, returns it. |
| **Subsequent visits** | Reads `focus_vid_v1` from localStorage. If valid hex 16-64 chars, reuses it. |
| **Corrupted/invalid stored value** | `loadStoredVisitorHash()` returns null (regex check fails). `getVisitorHash()` generates fresh + persists. Old value overwritten. |
| **Clear site data** | localStorage cleared → `focus_vid_v1` gone → next visit generates new ID. Previous `unique_views` remain valid (they were already counted). |
| **Incognito / private** | localStorage scoped to session → new ID per incognito session. Same-device dedup not possible across incognito sessions (by design). |
| **Authenticated user** | `visitor_hash` is still sent. We do NOT use `auth.uid()` for dedup. See rationale below. |
| **New browser / new device** | New localStorage → new ID. Unique views are not portable across devices (by design). |

### Why NOT use `auth.uid()` for dedup?

1. The showroom is **public** — most visitors are anonymous. `auth.uid()` only exists for a minority.
2. Mixing two identity namespaces (anonymous hash vs auth UUID) in the dedup key creates edge cases: "does this authenticated user's anonymous hash count as the same person?" Answer is always no.
3. `visitor_hash` is the consistent denominator. It works for everyone. Authenticated users who want cross-device identity can use favorites/purchase — that's a different feature.
4. The 1-hour dedup window is short enough that dual-identity confusion is negligible.

### Non-PII guarantee

- The hash is random, not derived from any user data.
- No IP, no fingerprint, no user agent, no device model stored.
- The server never sees anything that could identify a real person.
- **Privacy concern:** localStorage `focus_vid_v1` persists across sessions on the same browser. A local attacker with physical access could read it. This is a **low risk** — the value is meaningless without the database, and clearing site data resets it. This is acceptable for a phone marketplace view counter.

## C. View Definition

### Final Definition

```
A "view" is recorded when:
  1. ≥50% of the phone element's bounding rect is within the viewport
  2. The element remains continuously visible for ≥2 seconds
  3. The rate limit has not been exceeded for this visitor+device pair
  4. The dedup check passes (no duplicate within the last 1 hour)
```

### Analysis of thresholds

#### 50% visibility threshold

| Threshold | Verdict | Reason |
|---|---|---|
| 30% | Too low | A partially-visible card at screen edge counts as "viewed" |
| **50%** | **Chosen** | Half-visible = meaningfully seen. Standard in ad-tech. Matches `AdContactBanner.tsx` (which uses 0.6 — slightly higher because ads need stronger intent) |
| 70% | Too high | On mobile lists, fast scrollers may never reach 70% for cards near screen edges |
| 100% | Impractical | Full-viewport requires the entire card visible — impossible for tall cards on short screens |

**Decision: 50% (`threshold: 0.5`).** Balances false positives against false negatives.

#### 2-second duration

| Duration | Verdict | Reason |
|---|---|---|
| 1s | Too low | Passing glance during scroll = 1s. Not intentional. |
| **2s** | **Chosen** | Enough to read brand + model + price. Filters out scroll-by. Not so long that casual browsers are excluded. |
| 3s | Too strict | Penalizes quick-deciding users. |
| 5s | Absurd | Most phone cards are scanned in <3s. |

**Decision: 2000ms (`durationMs: 2000`).** The user can read the card info in this time.

#### Leave before 2 seconds

**The timer resets.** If the element drops below 50% visibility before 2s, the accumulated time is discarded. When it re-enters ≥50%, a fresh 2-second countdown starts.

Rationale: A scroll-past that briefly touches 50% for 0.5s then leaves is NOT a view. The user must sustain attention.

#### Does the timer reset on re-entry?

**Yes.** The implementation uses a simple accumulate-and-check pattern:
- Enter ≥50% → start accumulating time via `requestAnimationFrame` or `setInterval(100ms)`
- Exit <50% → discard accumulated time, clear timer
- Re-enter ≥50% → start fresh

This is clean, predictable, and prevents gaming via rapid scrolling.

#### Card view vs Detail view — one type or two?

**Two event types, same definition.**

| Event type | Where | What |
|---|---|---|
| `card_view` | `ShowroomScreen` phone grid | User scrolled a phone card into view for ≥2s |
| `detail_view` | `ProductDetailsScreen` | User stayed on the details page for ≥2s (entire page is "visible") |

Both use the same IntersectionObserver threshold and duration. The `event_type` column distinguishes them for analytics (e.g., "how many card views convert to detail views?").

**For `detail_view`:** The entire `<Screen>` is always ≥50% visible. Effectively this means "user stayed on the details page for 2+ seconds." A simpler implementation: `setTimeout(2000)` on mount → fire RPC if still mounted. No IntersectionObserver needed for detail_view because the page IS the viewport.

## D. Dedup Strategy

### Window: 1 hour

```sql
is_unique = NOT EXISTS (
  SELECT 1 FROM phone_view_events
  WHERE device_id = $1
    AND visitor_hash = $2
    AND recorded_at > now() - interval '1 hour'
)
```

| Window | Verdict | Reason |
|---|---|---|
| 10 min | Too short | User refreshes after 11 min → counts as unique again → inflated |
| **1 hour** | **Chosen** | Catches the same-session return. Long enough to prevent inflation from refresh. Short enough to count genuine re-visits across hours. |
| 24 hours | Too long | A user who returns tomorrow to buy a phone should count as a new engagement. |
| 7 days | Way too long | Loses legitimate re-engagement signal. |

### Dedup key: `(device_id, visitor_hash)`

A view is unique per device per visitor. Same visitor viewing two different phones = 2 unique views. Same device viewed by 100 visitors = 100 unique views.

### Does `auth.uid()` override `visitor_hash`?

**No.** The visitor_hash is always the dedup key regardless of auth status. See B for rationale.

### Is the event stored even if not unique?

**Yes.** Every accepted view (post-rate-limit) is inserted into `phone_view_events` with `is_unique = false`. This preserves the full event log for analytics and debugging. Only `is_unique = true` rows increment `unique_views`.

### How is the counter updated?

Inside the `record_phone_view()` RPC (atomic):

```sql
-- 1. Check dedup
is_unique := NOT EXISTS (
  SELECT 1 FROM phone_view_events
  WHERE device_id = p_device_id
    AND visitor_hash = p_visitor_hash
    AND recorded_at > now() - interval '1 hour'
);

-- 2. Insert event
INSERT INTO phone_view_events (device_id, visitor_hash, event_type, is_unique)
VALUES (p_device_id, p_visitor_hash, p_event_type, is_unique);

-- 3. Upsert counter
INSERT INTO phone_view_counts (device_id, total_views, unique_views, last_viewed_at, updated_at)
VALUES (p_device_id, 1, CASE WHEN is_unique THEN 1 ELSE 0 END, now(), now())
ON CONFLICT (device_id) DO UPDATE SET
  total_views  = phone_view_counts.total_views + 1,
  unique_views = phone_view_counts.unique_views + CASE WHEN is_unique THEN 1 ELSE 0 END,
  last_viewed_at = now(),
  updated_at = now();
```

## E. RPC Design

### `record_phone_view`

```sql
CREATE OR REPLACE FUNCTION public.record_phone_view(
  p_device_id    text,
  p_visitor_hash text,
  p_event_type   text DEFAULT 'view'
) RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_is_unique    boolean;
  v_total        integer;
  v_unique       integer;
BEGIN
  -- 1. Validate phone exists
  IF NOT EXISTS (SELECT 1 FROM inventory WHERE id = p_device_id) THEN
    RETURN jsonb_build_object('error', 'INVALID_DEVICE');
  END IF;

  -- 2. Validate visitor_hash format (non-PII, 16-64 hex chars)
  IF p_visitor_hash IS NULL OR p_visitor_hash !~ '^[a-f0-9]{16,64}$' THEN
    RETURN jsonb_build_object('error', 'INVALID_VISITOR');
  END IF;

  -- 3. Validate event_type
  IF p_event_type NOT IN ('card_view', 'detail_view') THEN
    RETURN jsonb_build_object('error', 'INVALID_EVENT_TYPE');
  END IF;

  -- 4. Rate limit: max 30 views per (visitor_hash, device_id) per hour
  IF EXISTS (
    SELECT 1 FROM phone_view_events
    WHERE device_id = p_device_id
      AND visitor_hash = p_visitor_hash
      AND recorded_at > now() - interval '1 hour'
    LIMIT 31 OFFSET 30
  ) THEN
    RETURN jsonb_build_object('error', 'RATE_LIMITED');
  END IF;

  -- 5. Dedup check
  SELECT NOT EXISTS (
    SELECT 1 FROM phone_view_events
    WHERE device_id = p_device_id
      AND visitor_hash = p_visitor_hash
      AND recorded_at > now() - interval '1 hour'
  ) INTO v_is_unique;

  -- 6. Insert event
  INSERT INTO phone_view_events (device_id, visitor_hash, event_type, is_unique)
  VALUES (p_device_id, p_visitor_hash, p_event_type, v_is_unique);

  -- 7. Upsert counter (atomic)
  INSERT INTO phone_view_counts (device_id, total_views, unique_views, last_viewed_at, updated_at)
  VALUES (p_device_id, 1, CASE WHEN v_is_unique THEN 1 ELSE 0 END, now(), now())
  ON CONFLICT (device_id) DO UPDATE SET
    total_views  = phone_view_counts.total_views + 1,
    unique_views = phone_view_counts.unique_views + CASE WHEN v_is_unique THEN 1 ELSE 0 END,
    last_viewed_at = now(),
    updated_at = now()
  RETURNING total_views, unique_views INTO v_total, v_unique;

  RETURN jsonb_build_object(
    'ok',         true,
    'total',      v_total,
    'unique',     v_unique,
    'is_unique',  v_is_unique
  );
END;
$$;
```

### `get_phone_view_counts`

```sql
CREATE OR REPLACE FUNCTION public.get_phone_view_counts(
  p_device_ids text[]
) RETURNS jsonb
LANGUAGE sql
SECURITY DEFINER
SET search_path = public
STABLE
AS $$
  SELECT COALESCE(
    jsonb_object_agg(
      device_id,
      jsonb_build_object(
        'total_views',  total_views,
        'unique_views', unique_views,
        'last_viewed',  last_viewed_at
      )
    ),
    '{}'::jsonb
  )
  FROM phone_view_counts
  WHERE device_id = ANY(p_device_ids);
$$;
```

### Transaction flow

```
Client calls record_phone_view(device_id, visitor_hash, event_type)
  │
  ▼
┌─ SECURITY DEFINER function (runs as postgres) ──────────────┐
│                                                              │
│  1. Validate device_id exists in inventory                   │
│  2. Validate visitor_hash matches ^[a-f0-9]{16,64}$         │
│  3. Validate event_type IN ('card_view', 'detail_view')      │
│  4. Rate limit: ≤30 events per (visitor, device) per hour    │
│  5. Dedup check: first event from this visitor in 1 hour?    │
│  6. INSERT into phone_view_events (is_unique = step 5)       │
│  7. UPSERT phone_view_counts (atomic increment)              │
│  8. RETURN { ok, total, unique, is_unique }                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
  │
  ▼
Client receives counts → updates local display (optional)
```

**Atomicity:** The entire function runs in a single PostgreSQL transaction. Step 6 and 7 are atomic by default (same `BEGIN...COMMIT`). If step 6 fails, step 7 never executes.

### Why not a third RPC?

No third RPC needed. The two RPCs cover:
- **Write path:** `record_phone_view` — fire-and-forget from client
- **Read path:** `get_phone_view_counts` — batch read for showroom listing + details page

If we later need aggregate analytics (top viewed, trend over time), those are **read-only admin queries** on the existing tables — no new RPC needed.

## F. Security / RLS

### RLS Policies

```sql
-- Public read: anyone can see aggregated counters
ALTER TABLE public.phone_view_counts ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Public read view counts"
  ON public.phone_view_counts FOR SELECT
  USING (true);

-- Staff read events (for admin/analytics)
CREATE POLICY "Staff read view events"
  ON public.phone_view_events FOR SELECT
  USING (public.ad_is_admin());

-- No direct INSERT/UPDATE/DELETE by clients on either table.
-- All writes go through record_phone_view() (SECURITY DEFINER).
```

### Table-level access

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| `phone_view_counts` | Public (RLS) | RPC only | RPC only | Admin only |
| `phone_view_events` | Staff (RLS) | RPC only | Never | Admin (retention cleanup) |

### SECURITY DEFINER

`record_phone_view` runs as the function owner (postgres). This means:
- The client never directly inserts into `phone_view_events`.
- The client never directly modifies `phone_view_counts`.
- All validation, rate limiting, and dedup happens server-side in a single transaction.
- Even if RLS is bypassed (it can't be with SECURITY DEFINER), the RPC validates everything.

### Abuse scenarios

| Scenario | Mitigation |
|---|---|
| Replay requests (same payload sent twice) | Dedup check: `visitor_hash + device_id + 1 hour window`. Second request returns `is_unique: false` but still increments `total_views`. If rate limit hit, returns `RATE_LIMITED`. |
| Concurrent requests (parallel AJAX) | PostgreSQL row-level locking on UPSERT. Two concurrent inserts into `phone_view_events` are serialized. Counter increment is atomic. |
| Bot sends 1000 requests | Rate limit: ≤30 per (visitor, device) per hour. Bot exhausts limit after 30, remaining 970 rejected. |
| Bot generates fake visitor_hash | Server validates format `^[a-f0-9]{16,64}$`. Each unique hash gets its own 30/hour budget. This is bounded — a bot can't exhaust the server's resources. |
| Client modifies `total_views` in display | **Client display is advisory only.** The database counter is authoritative. If client shows "50 views" but server says "45", the next `get_phone_view_counts` call corrects it. |
| Client sends `is_unique: true` from frontend | **Client never sends `is_unique`.** It's computed server-side in the RPC. The client only sends `device_id`, `visitor_hash`, `event_type`. |

## G. Rate Limiting

### Threshold: 30 views per (visitor_hash, device_id) per hour

#### Scenario analysis

| Scenario | Expected views/hour | 30 limit? |
|---|---|---|
| **Normal user browsing 20 phones** | 1 per phone = 20/hour | ✅ Fine |
| **Normal user browsing 50 phones** | 50/hour but spread across 50 devices → each device = 1/hour | ✅ Fine (limit is per device) |
| **User rapidly scrolling past 100 phones** | 0 — cards need 2s visible to count | ✅ Fine |
| **User refreshing the same phone 50 times** | 1 unique + 49 total (after dedup), but rate limit caps at 30/hour | ✅ Fine — 30 is enough for any reasonable refresh pattern |
| **Bot on single phone** | Would need 30 requests to exhaust | ✅ Fine — bounded |
| **Bot with 1000 fake visitor_hash** | Each gets 30/hour budget = 30,000 max total/hour | ✅ Acceptable — server can handle this easily, and it requires significant bot effort |
| **Multiple tabs open** | Same `focus_vid_v1` → same visitor_hash → shared budget | ✅ Fine — browser is one user |
| **User opens phone in detail, goes back, opens again** | 2 views (1 card_view, 1 detail_view) = 2/hour for this device | ✅ Fine |

**30/hour per (visitor, device) is appropriate.** The limit is per-device, so a user browsing 100 phones faces no bottleneck (each phone is a separate budget). The limit only kicks in for pathological repeated views of the SAME phone.

#### Why not lower (e.g., 10)?

A user who genuinely visits the same phone listing 15 times in an hour (comparing, showing friends, checking specs) would be rate-limited at 10. That's a real user scenario in a marketplace.

#### Why not higher (e.g., 100)?

Diminishing returns. No real user hits 100 views/hour/device. Higher limits just make rate limiting less protective against bots.

## H. Performance

### Cost analysis: `record_phone_view`

| Operation | Cost |
|---|---|
| Validate device exists | `SELECT 1 FROM inventory WHERE id = $1` — PK lookup, ~0.1ms |
| Validate visitor_hash | Regex check in PL/pgSQL — ~0.01ms |
| Rate limit check | `SELECT 1 ... LIMIT 31 OFFSET 30` with index on `(device_id, visitor_hash, recorded_at)` — ~0.2ms |
| Dedup check | `SELECT 1 ... WHERE recorded_at > now() - 1 hour` with same index — ~0.2ms |
| Insert event | Single row insert with index updates — ~0.5ms |
| Upsert counter | Single row upsert with index update — ~0.3ms |
| **Total** | **~1.3ms per RPC call** |

### Showroom grid with N phones

Current `ShowroomScreen` renders all phones in a CSS grid. The `useViewCounter` hook is currently only used in `ProductDetailsScreen`, NOT in the card grid.

**Proposed card_view tracking:**

Each `PhoneCard` will use IntersectionObserver. For a grid of N phones:

| N phones | IntersectionObserver instances | RPCs triggered (assuming 50% scroll-through) |
|---|---|---|
| 20 | 20 | ~8-12 (only phones that stay visible ≥2s) |
| 50 | 50 | ~15-25 |
| 100 | 100 | ~20-30 |

**Browser limit:** Modern browsers handle 100+ IntersectionObservers with no performance degradation (they share a single MutationObserver internally).

### Client-side optimizations

**None of these are the source of truth. The server is always authoritative.**

| Strategy | Purpose |
|---|---|
| **Debounce timer (2s)** | The IntersectionObserver callback doesn't fire an RPC immediately — it starts a 2s timer. If the element leaves before 2s, no RPC is ever made. This prevents unnecessary network requests. |
| **Session-level suppression** | A `Set<string>` (like the existing `countedThisSession`) tracks which device_ids have already had their RPC fired in this page load. Prevents double-counting from React re-renders. Reset on full page navigation. |
| **Fire-and-forget** | `record_phone_view` is called WITHOUT await. The client doesn't wait for a response. A failed RPC doesn't affect the UI. |
| **No batching needed** | Each view is an independent event. Batching adds complexity (partial failures, ordering) with no meaningful benefit — the RPCs are lightweight. |

### Preloading

`get_phone_view_counts` accepts `text[]` — the showroom screen calls it once with all visible device_ids:

```typescript
// In ShowroomScreen or useViewCounts hook
const counts = await getPhoneViewCounts(visible.map(d => d.id));
```

This is a single RPC returning all counters — no N+1 problem.

### Avoiding duplicate RPC calls

The new `useServerViewCounter` hook will:
1. Accept `device_id` and `event_type`
2. On mount → start 2s IntersectionObserver timer
3. On unmount or visibility exit → clear timer
4. On timer complete → fire `record_phone_view` (fire-and-forget)
5. Track fired device_ids in a module-level `Set` to prevent re-fires within the same page session

## J. Privacy

### What is stored

| Field | Stored? | PII? | Notes |
|---|---|---|---|
| `visitor_hash` | ✅ Yes (events table only) | ❌ No | Crypto-random hex. Not derived from any user data. Not linked to IP/auth/email. |
| `device_id` | ✅ Yes | ❌ No | Phone listing ID — public information. |
| `event_type` | ✅ Yes | ❌ No | `card_view` or `detail_view`. Behavioral metadata. |
| `is_unique` | ✅ Yes | ❌ No | Computed boolean. |
| `recorded_at` | ✅ Yes | ❌ No | Server timestamp. |

### What is NOT stored

| Data | Not stored | Why |
|---|---|---|
| IP address | ❌ | Never captured by the RPC. PostgreSQL doesn't log it by default. |
| User agent | ❌ | Never captured. |
| Device fingerprint | ❌ | Not computed. |
| Screen size | ❌ | Not captured. |
| Geolocation | ❌ | Not captured. |
| Auth user ID | ❌ | Not part of the view counter schema. |
| Email / name | ❌ | Not captured. |

### localStorage privacy concern

The `focus_vid_v1` identifier persists in localStorage. This means:

- **Same-browser tracking:** The same anonymous ID is used across sessions until site data is cleared. This is **intentional** — it's how we estimate unique visitors.
- **Cross-site isolation:** localStorage is origin-scoped. `focus_vid_v1` on `focus-app.com` is invisible to `other-site.com`.
- **Local attack surface:** Anyone with physical access to the device can read localStorage (e.g., via DevTools). The value is meaningless without the database. Risk: **low**.
- **Clear-site-data mitigation:** Users can clear site data to reset their identity. This is the expected privacy control.
- **Incognito:** Fresh identity per session. Users who browse in incognito will never be deduped across sessions — by design.

**Verdict:** The privacy model is acceptable for a phone marketplace view counter. The identifier is non-PII, the storage is origin-scoped, and the user has a clear opt-out (clear site data, use incognito).

## L. Final Recommendation

### What to build

1. **Migration `00029`:** `phone_view_counts` + `phone_view_events` + `record_phone_view()` + `get_phone_view_counts()` + RLS policies + indexes
2. **Client hook `useServerViewCounter`:** IntersectionObserver-based, 50% threshold, 2s duration, fire-and-forget RPC, session-level dedup
3. **Client hook `getPhoneViewCounts`:** Batch fetch for showroom grid display
4. **Replace `useViewCounter`** in `ProductDetailsScreen` with `useServerViewCounter(event_type='detail_view')`
5. **Add `useServerViewCounter`** to `PhoneCard` component with `event_type='card_view'`
6. **Delete old `useViewCounter`:** Remove the localStorage-only implementation

### Implementation order

1. Write migration SQL (tables + indexes + RPCs + RLS)
2. Write SQL unit tests
3. Write client hooks
4. Write client unit tests
5. Integrate into ProductDetailsScreen (detail_view)
6. Integrate into PhoneCard (card_view)
7. Add showroom batch-fetch for listing display
8. Run full test suite
9. Owner review → merge

### What NOT to build

- No IP logging
- No fingerprinting
- No auth-based dedup
- No client-side counter as source of truth (server is authority)
- No WebSocket / real-time counter updates (poll on page load is sufficient)
- No third RPC (admin analytics use direct SQL queries)
